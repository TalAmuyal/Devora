Thought experiment · not a plan of record

Devora, natively.

Suppose time and cost don't matter, and we rebuild Devora's UI as a real Mac app: Swift and AppKit/SwiftUI on the outside, a GPU-rendered native terminal in the middle, and the Rust core we already have underneath. This page shows what that app would look like, what it would be built with, what would change from Ember, and what it would honestly cost us.

TL;DR: Swift 6 + AppKit-hosted SwiftUI, libghostty for terminals, the existing Rust workspace logic extracted into a devora-core crate called through UniFFI, and WKWebView kept only where the content really is web (Crit, Mermaid). The biggest UX change isn't how it looks. It's that Devora starts telling you what Claude is doing: per-session state in a sidebar, notifications for pending permission requests, a Judge menu-bar extra, and Dock badges. The biggest cost isn't the code. It means giving up the Linux plan for the UI and starting a third UI generation.

1
Sidebar instead of a bottom tab bar. Sessions are a source list with a live Claude state per row (Working / Needs you / Plan ready / Idle), driven by Claude Code hooks posting to the IPC server. Today you can't tell a blocked tab from a busy one without switching to it. That's the single most valuable UX change here. ⌘1…9 switch sessions, and you drag rows to reorder.
2
Unified toolbar. Title = task title, subtitle = profile · workspace · repos (the window title also serves Mission Control and ⌘`). The Terminal / Review / Preview segmented control replaces the per-tab overlay layers from ADR-003.
3
The terminal is a Metal surface, not a DOM. libghostty draws it, and it handles IME, ligatures, font fallback, and the macOS text-input system. App shortcuts use ⌘, which terminals never use, so Ctrl+S, Ctrl+←/→, and friends go back to the shell/Neovim instead of being swallowed by Devora.
4
Inspector (⌥⌘I). Native per-worktree status (what gsum prints, as live views), the Judge decisions for this session, and the task's CLAUDE.md summary. Crit and previews open as a WKWebView in the Review/Preview modes.
5
Judge menu-bar extra. The design already in docs/future/judge-ember-menu-bar-integration.md, as a MenuBarExtra with full SwiftUI views (not a rebuilt-on-every-event NSMenu). Pending defers show as N⏸ next to the icon.
6
Actionable notifications (see the “Menu bar + notification” view). A deferred permission in a background session posts a UNUserNotification with Allow / Deny / Open buttons and badges the Dock icon. You can leave Devora in the background without forgetting a blocked agent.
7
Profile + health in the sidebar footer. Switching profiles is a menu, not a hub. The health dot turns amber/red when debi health would fail, and clicking it opens the Health view.
·
System design language for free. Vibrancy, sheets, focus rings, Liquid Glass, light/dark, accent color, reduced-motion, and VoiceOver all follow the OS. The Catppuccin theme stays where it belongs, inside the terminal, and becomes the app's accent tint.

What's kept

The rewrite covers the UI, not the product. Most of what makes Devora Devora lives outside the window.

The Rust core (~5.2k lines)

Profiles, workspaces, task creation, cloning, credentials, health. Extracted into devora-core, which helps Ember right away too.

The domain model

Profile, Workspace, Active Workspace, Session, Repo, Worktree, and Prepare Command keep their meanings. Only "Tab Bar" and "Terminal Pane (xterm.js)" go away.

The external contract

DEVORA_PTY_ID / IPC env vars and the JSON routes Judge, Crit, and debi preview already use. None of those tools need changes.

Keyboard-first, vim-flavoured (ADR-004)

Native doesn't mean mouse-first. createVimScroll / createListCursor become a SwiftUI modifier and an NSResponder mixin.

The acceptance specs

20 feature files and 119 scenarios become the parity checklist. When they all pass on the native driver, Ember can retire.

ccc, Judge, Code-Cleanup, debi, Status Line

Untouched. They are the parts with the most product value, and none of them have a UI of their own.

Costs & risks

"No time or cost constraints" doesn't make these go away, because some of them are strategic, not budgetary.

STRATEGIC

It closes the Linux door

The README promises Linux support "in the future". A native macOS UI means either a second native UI for Linux (GTK/Qt), or keeping Ember alive for Linux, which is two UIs forever. This is the real decision. Everything else is execution.

STRATEGIC

Third UI generation

Devora OG (Kitty + Glimpse-TTY) → Ember (Tauri) → Native. Ember just landed a whole layer-system redesign (#187, #188). Until parity, every feature is built twice or frozen.

HIGH

The agent dev loop gets slower

Devora is built largely by Claude. TS + Vite + happy-dom gives fast, headless, assertable feedback. Swift builds are slower, SwiftUI behaviour is harder to check without a running app, and visual checks need screenshots/XCUITest. Expect a lower development pace unless we invest in the test harness early.

MEDIUM

libghostty is not a stable public API

Its main embedder is Ghostty's own app. It needs the Zig toolchain in the build, a pinned commit, and a thin Swift wrapper so SwiftTerm can be swapped in if upstream churns. Licensing (MIT) is fine.

MEDIUM

Two UI frameworks to master

SwiftUI on macOS still needs AppKit escape hatches for focus, key handling, table performance, and text input. Contributors need both, and the boundary needs discipline (an ADR of its own).

MEDIUM

A lot of the visible wins don't need native

Notifications, tray/menu-bar, Dock badge, native menus, notarization, and auto-update all exist in Tauri 2. The native-only wins are terminal quality, true macOS chrome/feel, multi-window, accessibility, and system reach (Spotlight/Shortcuts/Services).

If we did it: the path

Ember stays the shipping product the whole way. Each phase has a gate, and the first one pays off even if we stop there.

0

Extract devora-core

Move profile/workspace/creation/clone/credentials/health out of src-tauri into a plain crate. Ember depends on it unchanged. Write the IPC routes down as a versioned spec.

Gate: Ember's Rust + e2e suites are green. Worth doing regardless of this decision.
1

Terminal spike

A bare window running ccc on libghostty and on SwiftTerm. Measure input latency, IME, resize, scrollback, ligatures, and Neovim inside it.

Gate: a clear winner, and a Swift wrapper API that hides which one.
2

Daily-drivable shell

Sidebar + sessions + terminal + IPC socket + Crit in WKWebView + Claude-state hooks. Add the test harness now, not later.

Gate: you can work a full day in it. session-management, crit-overlay, preview, and claude-hook-integration features pass.
3

Hub, New Task, Settings, Health

The rest of Ember's surface area, ported feature file by feature file.

Gate: all 119 scenarios pass on the native driver. Ember retires.
4

Native-only wins

Notifications with actions, Judge MenuBarExtra, Dock badge, restoration, App Intents, Spotlight, multi-window.

5

The vision docs

PromptEditor on embedded Neovim with native @// completion and {{snippet:…}} templates, used in the New Task sheet and for commit messages.

My honest verdict

As a product, the native version is clearly better. The terminal alone (no IPC hop, real input handling, ⌘ freeing up Ctrl) is something Ember can't match, and the macOS chrome stops it feeling like "a web page with a terminal in it."

But I'd only do it if you're ready to say "Devora's UI is macOS-only, for good." If Linux is a real goal, this doubles the UI work forever. If it isn't, then say so explicitly, update the README, and this becomes a reasonable long-term bet.

Either way, two things are worth doing now, in Ember: phase 0 (extracting devora-core, see the ticket) and the Claude-state-per-session feature (see the ticket) (hooks → IPC → tab status + notifications). That feature is the biggest UX win on this page, and it doesn't depend on the framework at all. Shipping it first also tells us how much of the remaining itch is really about "native".
