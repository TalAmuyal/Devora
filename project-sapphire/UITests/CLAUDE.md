# XCUITests

- The XCUITests launch the app themselves, each on a state directory of its own; `scripts/test-ui.sh` skips them, saying why, when the screen is locked or `SAPPHIRE_SKIP_UI_TESTS=1`.
	With little disk space left, macOS's cache_delete purges app container caches and has RunningBoard kill their apps, the UI test runner included, which XCTest reports only as "Test crashed with signal kill". When a run fails, `test-ui.sh` looks for that in the system log (`scripts/explain-ui-test-kill.sh`) and says so, with the free space: the cure is disk space, not the test.
	Each test has at most 5 minutes (`-maximum-test-execution-time-allowance`; the slowest passing one takes about 1). The first test that exceeds it, or whose app launch never gets a process, stops the whole run (`scripts/ui-test-watchdog.sh`, which `test-ui.sh` starts beside xcodebuild): once one hangs, the following ones usually hang the same way (a CI runner whose launch and screen-capture services wedged stalled every test after it), each for its full allowance. The watchdog reads XCTest's live logs in the bundle's `Staging/…/Diagnostics`, since xcodebuild's `-quiet` output holds those lines for its end summary.
	It names the test, leaves `build/ui-test-hang/` (the reason, a screenshot, samples of this build's app and runner, those logs, and how it stopped the run), and stops the xcodebuild `test-ui.sh` started, by its pid and start time: SIGINT, which still writes the result bundle (with XCTest's screenshot and spindump), then SIGKILL past a minute. A watchdog stop is not "the rest passed": the tests after the hung one never ran, so a test that's really too slow hides them until it's fixed.
	A wheel's scroll is animated over display frames, and a CI runner sometimes starves the app's window of them (`NativeTranscriptUITests`' `wheelScroll`, from the app's wheel trace). Before each wheel the test waits, up to 10 s, until the window has drawn a frame (the trace's `drawing:` heartbeat), and a window that stays frozen fails as "Runner problem, not the transcript" without a wheel sent. A scroll that doesn't land while one of its wheel events got 0 frames is the runner's too: it's sent once more, after the window draws again, and the retry is printed and attached ("Wheel retry: …"), so a runner that needs it often shows. That retry is only for this measured case, never for a scroll that failed with frames arriving, which is the transcript's failure; a second failure fails with both attempts' frame counts. Like a watchdog stop, a runner problem is an infrastructure failure, and the PR's owner may re-run the job, saying why on the PR.
	In CI, the Tests step has its own 40-minute limit for a hang between tests, and the result bundle, the watchdog's evidence (`sapphire-ui-hang-evidence`) and the acceptance captures are kept when a run is cancelled too.
	Those that close the launch's hub register a profile first (`writeConfigWithAProfile`), since the first-run welcome can't be closed.
	Their runner is sandboxed, where git can't run, so `scripts/test-ui.sh` makes the git repo they copy into their fixtures (`SAPPHIRE_GIT_REPO`), and the template the Agent settings test chooses in the open panel (`SAPPHIRE_AGENT_TEMPLATE`).

- XCUITest's synthesized input has no timing guarantee: on a busy machine its events can arrive seconds apart, so a UI test never depends on how quickly two of them arrive. A timing rule of the app takes its window as a parameter and is unit-tested on exact timestamps: `ShiftDoubleTap`'s 0.5 s, which the UI tests that tap Shift-Shift widen with `allowSlowShiftDoubleTaps` (`DEVORA_TEST_SHIFT_TAP_WINDOW`).
	`DEVORA_INPUT_TRACE` names a file where the app-wide shortcuts write each modifier event and how the double tap read it (`InputTrace`); `shiftShift` (`UITests/ShiftShift.swift`) attaches it, with whether the system still has Shift down, when Shift-Shift doesn't open the palette.
- XCUITest sometimes doesn't post a Shift release: the system still has Shift down seconds later. It happens most right after a relaunch, and also without one, on both of CI's runner images (a reopening gesture went press, release, press, with the last release never posted).
	Every real Shift-Shift goes through `shiftShift`, which sends the gesture once more, printed and attached ("Shift retry: …"), only when the palette didn't open and the system still has Shift down (`ShiftShiftCheck`); a gesture whose releases all arrived and didn't open the palette fails at once, as the app's failure.
	Still, no UI test taps Shift-Shift right after a relaunch, where it's most common: `GlobalPauseUITests` resumes with the toolbar, and real Shift-Shift is tested where nothing relaunches (`KeyRoutingUITests`).
- A wheel scroll goes through `scrollWithPointer` (`UITests/Launch.swift`), never `scroll(byDeltaX:deltaY:)` directly: XCUITest posts a scroll's events at the pointer's position, and its move to the target can land after them, sending them where the pointer was (the editor the test last typed into). The helper moves the pointer there and waits until the system reports it there.
- An XCUITest clicks only what's already in view, and brings a control there itself first (`scrollSettingsDetail(to:)`, built on `scrollWithPointer`): it never relies on XCUITest's own "scroll element to visible" before a click, which is the same wheel scroll, posted where the pointer rests.
	`scripts/test-ui.sh` (so `stress-ui` too) fails a run whose activity log shows one, naming the test and the action it scrolled for (`scripts/check-ui-scrolls.sh`), so a click that forgets fails on its first run rather than flaking later.

- In the XCUITests, a web view's text is found with `waitForText` (`UITests/Snapshots.swift`), never a `value` predicate: WebKit puts a heading's text in its `value` on older macOS, and on newer ones in its `title`, with its level as a number in `value`, which makes `value CONTAINS` throw.
- Every XCUITest action and query resolves through a snapshot of the app's accessibility tree, which is slow when the tree is big (an open panel listing a big directory has thousands of elements). Keep what a test shows small, with fixtures in `build/ui-test-fixtures` (made by `scripts/test-ui.sh`) rather than the runner's container, and check several things in one snapshot (`waitForSnapshot`) rather than one query each.
